# 案例研究模板框架

> 用途：把做过的 Power BI 项目写成可发布、可复用、能带来咨询的内容。
> 一份案例 = 一篇公众号长文 + 一期 B 站视频 + 若干知乎/小红书切片，素材一次采集，多次使用。
> 目标读者是「正在被同一个问题折磨的人」，不是同行评审。

---

## 0. 写作前先填这张卡（15 分钟，填不出来就别写）

| 字段 | 填写 |
| --- | --- |
| 一句话结论（≤30 字） |  |
| 主角行业 / 规模 |  |
| 原来多久出一张表 / 现在多久 |  |
| 最反直觉的一个决策 |  |
| 能公开的数字（前后对比） |  |
| 不能公开的内容（客户名、金额、系统名） |  |
| 这篇给谁看 |  |
| 结尾想让读者做什么 |  |

红线：客户名、具体金额、未脱敏的系统截图、可反推到个人的信息，一律不写。数字要么真实可公开，要么不写。

---

## 1. 标题（三种写法，选一个）

- 结果型：`3 天出表压到 30 分钟：一家制造企业的 Power BI 改造`
- 问题型：`报表打开要 8 秒？我们只改了三处`
- 决策型：`SAP 取数慢，为什么最后没换 ETL 工具`

标题里必须有一个具体名词或数字；不超过 22 字；不用「浅谈」「深入」「赋能」。

---

## 2. 开头：先给结论（150 字以内）

三句话讲完：

1. 谁的问题（行业 + 角色，不写公司名）
2. 原来的代价（时间、人力、错误率）
3. 现在的结果（一个可验证的数字）

> 范例：某制造企业的财务月结报表，原来靠三个人手工拼 Excel，每月前五天基本耗在这上面。我们把 SAP BW 的数据接进 Power BI 语义模型，月结报表从 3 天缩到 30 分钟，口径只维护一份。

---

## 3. 背景（200–400 字）

- 业务背景：这个报表服务什么决策，谁在看
- 数据现状：系统有哪些（SAP ERP / BW、Databricks、Excel、数据库），数据量级
- 团队现状：有没有 IT 支持，谁维护
- 之前的尝试：做过什么、为什么没成（这是最值钱的部分）

---

## 4. 问题拆解（核心章节）

不要罗列症状，按「表面现象 → 直接原因 → 根因」三层写，至少拆一条：

| 表面现象 | 直接原因 | 根因 |
| --- | --- | --- |
| 报表打开要 8 秒 | 模型里有 40 个双向关系 | 没有维度建模，直接拿明细表建模 |
| 每月对不上数 | 财务和业务各算一套 | 指标没有统一定义，缺度量值规范 |

然后给一句话判断：**这个问题本质上是数据问题、模型问题，还是流程问题？** 这决定了后面方案的方向。

---

## 5. 方案（配图：一张架构图 + 两张模型/报表截图）

1. **总体架构**：数据从哪来、怎么进来、在哪建模、谁消费。用一张横向图讲完。
2. **关键技术选择**：每做一个选择，写「选了什么 / 为什么 / 放弃了什么」。
   例：增量刷新而不是全量导入——数据量大且只需看近两年；代价是历史修正要走一次全刷。
3. **语义模型**：星型模型结构、关键度量值、命名规范。贴一段最有代表性的 DAX（10 行以内，带注释）。
4. **交付物**：几页报表、几块看板、有没有培训、有没有文档。

> 图比字重要：架构图、模型关系图、改前改后对比图，各一张。截图要脱敏，数字可以换成比例。

---

## 6. 实施过程（300–500 字）

按阶段写，不要按时间流水账：

| 阶段 | 做了什么 | 耗时 | 关键决策 / 踩的坑 |
| --- | --- | --- | --- |
| 摸底 |  |  |  |
| 建模 |  |  |  |
| 报表开发 |  |  |  |
| 试运行 |  |  |  |
| 交接 |  |  |  |

**踩坑部分决定这篇的可信度**：写一个真实的坑、怎么发现的、怎么修的，比十句「效果显著」有用。

---

## 7. 成果（必须是表格）

| 指标 | 改造前 | 改造后 | 口径 / 测量方式 |
| --- | --- | --- | --- |
| 月结报表出表时间 | 3 天 | 30 分钟 | 从关账到报表可看 |
| 维护人力 | 3 人 | 1 人 | 每周投入工时 |
| 报表打开耗时 | 8 秒 | 1 秒 | 首屏渲染，桌面端 |
| 指标口径 | 3 套 | 1 套 | 财务与业务对账一致 |

规则：
- 每个数字都要能说清怎么量的，说不清就不写。
- NDA 限制时用区间或比例：`耗时下降约 80%`，并注明「按客户要求脱敏」。
- 不写「效率提升 300%」这类没口径的倍数。

---

## 8. 客户评价（可选，1–2 句）

有原话就引用并注明角色（「财务总监」），没有就不写，不要编。

---

## 9. 可复用的经验（3–5 条，每条一句话）

> 例：先定指标口径再建模，返工能少一半。
> 例：SAP BW 的查询在 BW 侧做聚合，别指望 Power Query 里补。

这一节是给同行和潜在客户看的「专业度证据」。

## 11. 脱敏检查清单（发布前逐条打勾）

- [ ] 客户名称、品牌、Logo 已移除或替换为「某制造企业」
- [ ] 截图里无真实人名、工号、手机号、邮箱、内部系统地址
- [ ] 金额、销量等敏感数字已改为区间或比例
- [ ] 组织架构、系统拓扑不含可反推信息
- [ ] 客户已口头或书面同意公开（涉及合作方时必须）
- [ ] 引用的第三方数据有出处

---

## 12. 分发改写

| 载体 | 长度 | 改写要点 |
| --- | --- | --- |
| 公众号长文 | 2000–4000 字 | 用本模板全文，配 4–6 张图 |
| B 站视频 | 8–12 分钟 | 只讲「问题 → 一个关键决策 → 结果」，屏幕录制操作过程 |
| 知乎回答 | 600–1000 字 | 找对应问题，先答结论，再放案例，末尾放链接 |
| 小红书 / 视频号 | 60 秒 / 300 字 | 只留最反直觉的那一个点 + 一张对比图 |
| LinkedIn | 150 词英文 | 结果 + 方法 + 一句 CTA，不贴长文 |

---

## 13. 发布检查

- [ ] 标题含关键词（Power BI / DAX / SAP / 语义模型，按主题选一个）
- [ ] 首段 150 字内含结论和数字
- [ ] 至少三张图，全部脱敏
- [ ] 内链到官网（带 UTM）和作品集
- [ ] 公众号摘要 ≤ 54 字
- [ ] 发布后 24 小时内看一次数据：完播率、收藏、加微信数
