DAX 度量值跑得慢？先定位，再改这 6 处

DAX 慢，多半不是公式写法，是没定位。6 个技巧，每个给前后对比。

  • Power BI
  • DAX
  • 性能优化
  • DAX Studio
  • VertiPaq

DAX 性能优化的第一步不是改公式，是量。同一张报表卡，可能是 DAX 查询慢，可能是视觉对象太多，也可能是模型里有一列根本不该进来。改错地方，公式写得再漂亮也没用。

这篇按「先定位、再改写、最后看模型」的顺序讲 6 个技巧。每个都给改前和改后的写法，你能直接对照自己手上的度量值。要有人帮你把整份报表过一遍，服务 页写了范围；只是想先把手上的慢查询压下去，照着做就行，卡住了从 联系 页找我。

先定位：Performance Analyzer 看的是两段时间

视图 → 性能分析器 → 开始记录 → 刷新页面或单个视觉对象。每一行有两列关键数字：DAX 查询时间和视觉对象显示时间。

  • DAX 查询时间高：引擎在算，往下看公式和模型。
  • 视觉对象显示时间高、DAX 时间低：数据早就回来了，卡在渲染。多半是表格列太多、卡片堆太密、一页刷十几个视觉对象。
  • 两者都低但页面还是慢：查网络、网关、容量，不是 DAX。

定位到具体视觉对象后，把它的 DAX 查询复制到 DAX Studio，打开 Server Timings，再点 Clear Cache。看两个数：FE（Formula Engine，公式引擎，单线程）和 SE（Storage Engine，存储引擎，多线程）。SE 时间长，通常是扫描的数据量太大；FE 时间长，通常是公式结构复杂、迭代次数多。

注意一点：不清缓存，第二次测的是缓存结果，数字会好看到失真。

技巧 1：能算一次的，别算两次

同一个表达式在一次求值里被引用多次，用 VAR 收起来。

改前：

同比增长率 =
DIVIDE(
    [销售额] - CALCULATE([销售额], SAMEPERIODLASTYEAR('日期'[Date])),
    CALCULATE([销售额], SAMEPERIODLASTYEAR('日期'[Date]))
)

改后：

同比增长率 =
VAR 本期 = [销售额]
VAR 同期 = CALCULATE([销售额], SAMEPERIODLASTYEAR('日期'[Date]))
RETURN DIVIDE(本期 - 同期, 同期)

公式引擎不用把同一个 CALCULATE 解析两遍，公式也读得懂。

注意：VAR 不是缓存。它只在当前这一次求值里生效，不会跨行、跨视觉对象复用。别指望加几个 VAR 就把慢查询救回来——它解决的是重复计算和可读性，不是数据量。

技巧 2：迭代器只迭代该迭代的行

SUMX、AVERAGEX、MAXX 都是迭代器：对一张表逐行算，再把结果聚合。慢不慢，取决于你喂给它多少行。

改前：

大单销售额 =
SUMX(
    FILTER(Sales, Sales[Amount] > 1000),
    Sales[Amount] * Sales[Qty]
)

FILTER 会先把整张 Sales 物化成一张新表，再逐行迭代。

改后：

大单销售额 =
CALCULATE(
    SUMX(Sales, Sales[Amount] * Sales[Qty]),
    Sales[Amount] > 1000
)

布尔条件交给 CALCULATE，引擎会把它翻译成对 Sales[Amount] 这一列的筛选，不用先造表。

注意：条件跨两张表、或者需要 OR 组合时，FILTER 仍然是对的写法。但把它套在最小那张表上，别套事实表。

技巧 3：计算列、度量值、Power Query，选对计算发生的层

计算列在刷新时算一次，按行存进 VertiPaq，占内存；度量值在查询时按视觉对象的粒度算，不占存储。事实表上的计算列，几百万行就是几百万次计算，还会抬高模型体积。

改前，在 Sales 事实表加计算列：

利润 = Sales[Amount] - Sales[Cost]

改后，改成度量值：

利润 = SUM(Sales[Amount]) - SUM(Sales[Cost])

度量值只算当前视觉对象需要的那些行。

什么时候该用计算列：这一列要拿来切片、分组、做关系键，度量值做不到。即便这样，也先看 Power Query 能不能做——能在刷新前的 M 里算完的，别留到 DAX。

注意：SUM(A) - SUM(B) 和逐行相减再求和的结果一样，但涉及除法、空值、单位换算时，先确认口径再换。

技巧 4：别在度量值里做模型该做的事

有些慢，改公式救不回来，问题在模型。

  • 高基数无用列：订单号、时间戳、备注，基数几十万上百万，压缩率极低。不用就删。
  • 双向关系：筛选器传播路径变多，查询计划变复杂。需要时用 CROSSFILTER 在单个度量值里局部打开：
按客户看销售额 =
CALCULATE(
    [销售额],
    CROSSFILTER(Customer[CustomerKey], Sales[CustomerKey], BOTH)
)
  • 没标记的日期表：时间智能函数会退化成逐行扫描。日期表要连续、无重复、标记为日期表。
  • 事实表直接对事实表建关系：先想清楚粒度，多数情况该补一张维度。

之前做的 FinOps 看板有 27 个业务单元、28 个 RLS 角色，这种模型里双向关系尤其要克制：每多一条，RLS 的筛选就要多传播一次。

技巧 5：把筛选条件写简单，让引擎少猜

CALCULATE 的筛选参数越简单，引擎越容易走索引式扫描。

改前：

华东销售额 =
CALCULATE(
    [销售额],
    FILTER(ALL(Region), Region[RegionName] = "华东")
)

改后：

华东销售额 =
CALCULATE(
    [销售额],
    Region[RegionName] = "华东"
)

第二种是列筛选，引擎直接定位；第一种先解除筛选、再物化、再过滤。

注意：需要保留外部切片器时加 KEEPFILTERS；需要跨表条件时才回到 FILTER。

技巧 6：Direct Lake 慢，先查表是怎么写的

如果模型是 Direct Lake，DAX 可能根本不是瓶颈。

Data Mozart 上个月做过一组测试：同一个 5 亿行的数据集，写成七张 Delta 表，每张只改一个变量——文件数、row group 大小、V-Order、分区方式。然后用同一个 Direct Lake 模型跑同样的查询。结果很直接：数据进内存之后，七张表都在半秒内返回；差别全在冷查询，也就是把数据读进内存那一次，从 0.8 秒到 14 秒不等。

所以 Direct Lake 报表第一次打开慢、后面快，先查这几件事：

  1. 表是不是小文件太多，或者单个文件太大。
  2. 有没有开 V-Order。
  3. 分区键是不是和常用筛选对得上。
  4. 容量有没有触发 guardrail，导致表被踢出内存。

这些都不是 DAX 能解决的。改公式之前，先确认慢在哪一层。

常见问题

用了 VAR，为什么没变快？

VAR 只避免同一次求值里的重复计算，不会减少扫描的行数。如果瓶颈是 SE 时间，也就是读数据的量，VAR 帮不上。先看 Server Timings 里 FE 和 SE 谁占大头。

计算列一定比度量值慢吗？

不是一定，但代价不同。计算列在刷新时算、按行存、占内存；度量值在查询时算、不占存储。事实表上的高基数计算列最容易拖慢模型。维度表上几十行的计算列，影响可以忽略。

DAX Studio 里 FE 和 SE 分别是什么？

FE 是公式引擎，负责解析公式、做上下文转换和迭代，单线程；SE 是存储引擎，负责扫描和聚合 VertiPaq 数据，多线程。SE 时间长说明读得太多，FE 时间长说明算得太碎。

报表第一次打开慢，第二次快，是 DAX 问题吗？

多数不是。第一次要把数据读进内存，后面命中缓存。Import 模型看容量和内存，Direct Lake 看表文件和 framing。这种情况改 DAX 基本无效。

我的判断

优先级排一下：

必学：Performance Analyzer 和 DAX Studio 的 Server Timings。不会量，就只能猜。这两个工具半小时能上手，收益比背二十个函数大。

必学：VAR。哪怕不提速，公式的可读性也值回票价。团队协作里，一条能一眼看懂的度量值比省 50 毫秒重要。

可选：SUMX、FILTER 的改写。数据量在百万行以下、页面响应在 2 秒以内，别折腾。到了千万行、或者 SE 时间明显偏高，再按第 2、5 条改。

优先级最高但最容易被跳过：模型层。删无用列、克制双向关系、标记日期表，这三件事的收益通常比改十条公式大。想先看一份模型检查清单，博客 里有更细的拆解。

什么情况下别做：报表只有几十万行、刷新和打开都在 2 秒内，优化是浪费。Direct Lake 冷查询慢，也别从 DAX 下手——先去看 Delta 表是怎么写的。

你手上最慢的那个视觉对象，DAX 查询时间和显示时间各是多少？先看这两个数，再决定改哪里。
